# RAG 与向量检索笔记

## 为什么 LLM 需要"外挂知识"

大模型的知识来自训练数据，训练完成后就固定了。它不知道：

- 你昨天写的日记
- 公司内部的产品文档
- 今天早上刚发布的新闻

一种笨办法是把这些资料一股脑塞进 prompt。但 prompt 有长度限制，而且每次调用都发一遍成本爆炸。

## RAG 的思路

Retrieval-Augmented Generation（检索增强生成）。

先把私有知识切成很多小段，事先转换成一种叫向量（embedding）的表示 —— 一个浮点数组。语义相近的文字对应的向量在高维空间里靠得近，我们可以用余弦相似度衡量这种"近"。

用户提问时，把问题也变成向量，从数据库里挑出几段最相关的，塞进 prompt 给 LLM 参考。这样：

1. Context 不会爆炸（只塞相关的几段）
2. 知识可以随时更新（只需重新入库，不用重训模型）
3. 答案有出处，可以显示引用

## 一个完整流水线包含哪些步骤

**Ingest 阶段（一次性）**：
- 加载原始文档（Markdown、PDF、HTML……）
- 切分成 chunk（一般 200-800 字）
- 每个 chunk 转成向量
- 存入向量数据库

**Query 阶段（每次提问）**：
- 用户输入 → 向量
- 数据库返回 top-k 最相似的 chunk
- 把 chunk 拼进 prompt
- 调 LLM 生成回答

## 向量数据库选型

- **Chroma**：本地文件存储，`pip install chromadb` 就能用，适合小项目和原型
- **Qdrant**：开源，性能好，可自部署
- **Pinecone**：SaaS，托管方便，付费
- **Milvus**：大规模企业级
- **pgvector**：PostgreSQL 插件，如果你已经在用 PG 可以直接加

小项目直接 Chroma 就够了。数据量大了再考虑迁移。

## Chunking 是隐藏的关键

切分策略直接影响检索质量。太碎信息不足，太粗混入噪音。常见做法：

- 按段落 + 字数上限（简单，我们 Day 3 用的就是这个）
- 按 Markdown 标题分层
- 按句子边界
- 语义切分（用小模型判断边界）
- 加 overlap（相邻块重叠一部分，避免关键内容被切断）
